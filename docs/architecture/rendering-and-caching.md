# Rendering and caching

Mathimator never asks Manim to render part of a scene. Every preview and every
export renders the whole generated `scene.py`, and Manim's own partial-movie
cache makes that cheap: each beat is one `self.play` or `self.wait`, Manim
writes one *partial movie* per call, and it reuses the partial movie of every
call whose code and starting state are unchanged. Mathimator's job is to
generate code that keeps those calls stable, to know which partial movies
belong to which beat, and to never trust a cut-off file.

The rules are in sections 4 to 7 of [the design spec](../design-spec.md). The
code is in [`codegen.py`](../../worker/mathimator_worker/codegen.py),
[`identity.py`](../../worker/mathimator_worker/identity.py),
[`progress.py`](../../worker/mathimator_worker/progress.py),
[`preview_index.py`](../../worker/mathimator_worker/preview_index.py),
[`clip_check.py`](../../worker/mathimator_worker/clip_check.py) and
[`exports.py`](../../worker/mathimator_worker/exports.py).

## Scene generation

[`codegen.generate`](../../worker/mathimator_worker/codegen.py) turns a
document into the text of `scene.py`. The same document always gives the same
bytes. A scene with an axes, a plot and a formula, each entering in turn,
followed by a wait, compiles to:

```python
# Generated by Mathimator. generatorVersion 2. manim==0.22.0
from manim import *
import numpy as np

config.seed = 1


class MainScene(Scene):
    def construct(self):
        self.camera.background_color = "#000000"

        axes_1 = Axes(
            x_range=[-6.5, 6.5, 1],
            y_range=[-1.5, 1.5, 0.5],
            x_length=10,
            y_length=4,
            axis_config={"color": "#FFFFFF"},
        )
        axes_1_labels = axes_1.get_axis_labels(x_label="x", y_label="y")
        axes_1_group = VGroup(axes_1, axes_1_labels)
        self.play(Create(axes_1_group), run_time=2)

        plot_1 = axes_1.plot(
            lambda x: np.sin(x),
            x_range=[-6.28, 6.28],
            color="#58C4DD",
        )
        self.play(Create(plot_1), run_time=3)

        title_1 = MathTex(r"y = \sin(x)", color="#FFFFFF")
        title_1.to_edge(UP)
        self.play(Write(title_1), run_time=2)

        self.wait(1)
```

The header sets the seed, imports Manim and numpy, and defines `MainScene`,
a `Scene` or, for the 3D template, a `ThreeDScene` whose opening camera is one
`set_camera_orientation` call. The file sets no resolution, frame rate or
format: those come from the command line, so the same file serves the preview
and every export.

Each beat is one block:

1. **Construction** of each object the beat brings on screen (an entrance's
   targets, a morph's destination), axes before what is drawn on them. Every
   entrance builds its object afresh from its fields, so an object that leaves
   and comes back looks as its fields define it, whatever earlier beats did.
2. **Preparation**, such as measuring the shared centre of several targets
   that scale or rotate together, or saving a target's state.
3. **The one call**: `self.play(<animations>, run_time=...)`, or
   `self.wait(...)` for a wait, or `self.move_camera(...)` for a camera move.
   A beat on several objects plays one animation per object, never a group,
   because Manim would draw a played group above everything else from then on.
4. **Settling**, such as restoring a saved state, so the next beat starts from
   an exact, frame-rate-independent state.

The animation of each kind comes from its catalog row in
[`beats.py`](../../worker/mathimator_worker/beats.py) (`call` and
`centred_call`). An easing becomes `rate_func=<easing>`, written only when the
beat names one or when the kind's default is not the animation's own, so a
beat on its default easing compiles to the code it always did. `uncreate` and
`unwrite` run their rate function backwards in Manim, so codegen writes the
mirror image of the stored easing.

Expressions are translated by [`expr.py`](../../worker/mathimator_worker/expr.py)
from the fixed grammar to numpy calls (`sin(x)^2` becomes `np.sin(x) ** 2`),
never evaluated. Formula LaTeX goes into `MathTex` as a raw string. Document
numbers are written with up to three decimals; numbers inside an expression
are written exactly as typed.

The tests that hold the generated code in place:

- [`scenes/reference_60.py`](../../scenes/reference_60.py) and the examples in
  section 5 of the spec are compared byte for byte.
- [`tests/fixtures/beats/codegen.json`](../../tests/fixtures/beats/codegen.json)
  holds the blocks of every kind, shape and easing.
  `uv run pytest tests/test_codegen_beats.py --update-golden` rewrites it.
- [`tests/fixtures/beats/legacy-goldens.json`](../../tests/fixtures/beats/legacy-goldens.json)
  records documents written before the beat catalog grew. They must keep their
  bytes, their `scene.py` and every cache key. It is never rewritten.

## The frame rule

A beat runs from its derived start to its end, the next beat's start. At the
frame rate of the render, it covers the frames from `round(start × fps)` up to
`round(end × fps)`, halves rounded up. So every beat boundary is within half a
frame of the timeline at every frame rate, and a scene of `T` seconds has
`round(T × fps)` frames.

A beat whose start and end are both whole seconds keeps its duration as a
literal, as above. Any other beat calls `_beat_time(start, end)` for its
`run_time`, or `self.wait(_beat_time(start, end, wait=True))`, and the header
then defines the helper (shown here without its comments):

```python
def _beat_time(start, end, wait=False):
    rate = config.frame_rate
    frames = (round(end * 1000) * rate + 500) // 1000 - (round(start * 1000) * rate + 500) // 1000
    if wait:
        return (frames + 0.5) / rate
    return max(frames - 0.5, 1) / rate
```

The helper reads the frame rate when the scene renders, so one `scene.py`
still serves every profile. It counts in whole milliseconds with integer
arithmetic, because in floating point 4.1 × 15 is 61.4999… and would round the
wrong way. Manim draws `ceil(run_time × fps)` frames for a play and
`floor(seconds × fps)` for a still wait, so the helper adds or removes half a
frame of slack to land on the exact count either way.

The same integer rule appears in two more places, and they must agree:
[`playback.ts`](../../desktop/src/playback.ts) maps the playhead to a frame,
and `exports.export_frame_count` counts the frames a PNG sequence must have.
[`tests/fixtures/timing/frame-boundaries.json`](../../tests/fixtures/timing/frame-boundaries.json)
lists boundaries and their frames for the worker's and the UI's tests.

## Partial movies and Manim's cache

Manim keys each play on its code and on everything on screen when it starts,
and reuses an existing partial movie for a matching key. So when beat `i`
changes, Manim renders beat `i` and every beat after it, and reuses beats
`0` to `i - 1`. Codegen keeps the code of every beat before the first change
byte-identical, which is what keeps that prefix cached. The header may gain or
lose the `_beat_time` helper when a duration edit makes a boundary fractional,
but Manim does not hash the header.

A few details keep Manim's keys stable:

- `PYTHONHASHSEED=0` in Manim's environment, because Manim's key for a play
  that holds a function (a rotation path, a wave) lists that function's
  global names in the order of Python's string hashing.
- Moving along a path and wiggling put their objects back exactly after the
  play, and a camera move resets the camera's rotation to where the move ends,
  because where Manim leaves them depends on the frames drawn, and that state
  would change the key of every later play.
- `--seed` and `config.seed` are the project's seed, and codegen emits no
  random calls and no updaters.
- [`manim.cfg`](../../worker/mathimator_worker/manim.cfg) raises
  `max_files_cached` to 2400, so Manim never evicts the clips of the render
  that just finished (a document has at most 1200 beats).
- `--max-inflight-encoders 1` makes Manim finish each partial movie before it
  starts the next beat, which is what lets the worker follow progress through
  the files.

Preview and export share one media folder, `.mathimator/cache/media`. Manim
keeps each size and frame rate in its own quality folder,
`videos/scene/<height>p<fps>`, so a 480p15 preview clip is never used for a
1080p30 export, but an export after an earlier export at the same profile
reuses that profile's clips.

## Cache identity

[`identity.py`](../../worker/mathimator_worker/identity.py) computes SHA-256
hashes of canonical JSON payloads (sorted keys, no whitespace, three decimal
places). Display names are left out of every payload, so renaming an object or
the project neither dirties a preview nor throws away an export.

| Identity | Payload | Used for |
| --- | --- | --- |
| Beat key (`beat_cache_keys`) | The Manim version, `generatorVersion`, the profile (preview or export), the beat's index, the beat, the objects it names (with the axes that a plot, point, surface or curve is drawn on) and the seed. The beat's `easing` is included only when it names one | Dirty flags |
| Scene stamp (`scene_stamp`) | The background, the camera, the scene kind, `schemaVersion`, `generatorVersion` and the seed | Dirty flags: a change dirties every beat |
| Chain key (`beat_chain_keys`) | The scene stamp, hashed in turn with the beat keys of beat 0 up to beat `i` | Whether a preview file is fresh |
| `sceneHash` (`scene_hash`) | `schemaVersion`, `generatorVersion`, the seed and the scene | The export key |
| `exportKey` (`export_key`) | `sceneHash`, the export profile and the Manim version | The export folder `exports/<key16>/` and its `export.json` |

**Dirty flags.** When a preview finishes, the worker records the scene stamp
and the beat keys in `cache/rendered.json`. A beat is dirty when its key or
the key of any beat before it differs from that record, and every beat is
dirty when the scene stamp differs. Editing beat `i` therefore marks `i` to
the end dirty, as Manim will render them again. A change to an object marks
dirty from the first beat that names it, which may be the first beat: that is
the coarseness of caching at the play boundary.

**Freshness.** A partial movie shows the scene as every earlier beat left it,
so a file belongs to a document only while its chain key matches. The preview
index stores each file with the chain key it was rendered for. An undo
therefore brings back a beat's earlier file as fresh when that file still
exists, and a file from another document never shows without the "out of
date" badge.

The payloads change only together with `GENERATOR_VERSION`.
[`tests/test_characterization.py`](../../tests/test_characterization.py) pins
their values, so a refactor that changed a key by accident fails.

## Following a render

While Manim runs, the worker sends each finished preview beat as `beat_ready`.
[The worker page](worker.md#progress-and-the-preview-index) describes how
[`ManimProgress`](../../worker/mathimator_worker/progress.py) tells which file
belongs to which beat: it records the quality folder before Manim starts, takes
each new partial that is complete and older than the newest as the next beat
Manim renders, and lets the segment list Manim writes at the end settle the
order of every beat, reused ones included.

Two cases make it wait for the segment list instead of guessing: partials with
the same modification time, and any beat after the first camera move, because
a state the camera move leaves could make Manim render a later beat again that
the index counts as fresh.

## Clip validation

Manim reuses any partial movie that exists, complete or not, so one cut-off
file would break every later render of its beat.
[`clip_check.clip_is_complete`](../../worker/mathimator_worker/clip_check.py)
reads the container structure with the standard library:

- **MP4 and MOV**: the top-level boxes add up to exactly the file length, none
  has size 0 (FFmpeg's placeholder until it closes the file), and one is
  `moov`, which FFmpeg writes last.
- **WebM**: an EBML header, then top-level elements of known size that add up
  to exactly the file length, one of them a Segment, whose size FFmpeg fills in
  when it closes the file.

`ClipChecker` remembers the files that passed by size and modification time.
The worker uses the check at every step where a cut-off clip could slip in:

- **Before a render**, it deletes the incomplete partials in the job's quality
  folder, so their beats render again.
- **While a preview runs**, a partial counts as finished only when it is
  complete.
- **After a render that exits 0**, every clip in the segment list must be
  complete. If Manim used an incomplete one, that clip is deleted, nothing is
  recorded or published, and the job fails with `render_failed` "manim used an
  incomplete clip <file>; it was removed, so render again". The UI offers
  Render again.
- **After a cancel or a failure**, `ManimProgress.discard` deletes what the run
  wrote that may be cut off: an incomplete partial, the segment list and the
  scene movie. Complete partials stay, so the next render reuses them.
- **After a crash**, the run marker `cache/manim-run.json` holds the record of
  what the quality folder held before the run. The next bind of the folder
  deletes what the run wrote by the same comparison, then the marker.
- **When the index is rebuilt**, after every change and every bind, only files
  that pass the check count.

## Exports and re-export

An export renders at the export profile into its own quality folder, then is
published by [`exports.publish_export`](../../worker/mathimator_worker/exports.py):

- The output must be in the project's media folder, in the export's quality
  folder, of the right type, and not the preview. This guard keeps a 480p15
  preview from ever being published as an export.
- A PNG sequence must have as many frames as Manim reports and as the
  document has at the export frame rate. Manim writes every PNG sequence into
  one folder and never empties it, so the worker deletes that folder before
  each PNG export.
- The file is copied to a temporary name in `.mathimator/exports/<key16>/` and
  renamed over the published one; a folder is moved aside first and moved back
  if the new one cannot take its place. Then `export.json` is written the same
  way, with the full export key. A failure leaves the older file and its
  manifest as they were, and the job fails with `publish_failed`.

An export whose `export.json` records the current export key is the current
export. A repeat export finds it and answers `done` at once, without starting
Manim. **Re-export** sends `force: true`, which skips that check and renders
again; Manim still reuses the cached clips of that profile, and the older file
stays until the new one replaces it.

If the document changes while an export runs, the export goes on for the
document as it was when it started. When it finishes, `done.current` is false,
and the UI notes "This file is from an older export."

## When to bump GENERATOR_VERSION

`GENERATOR_VERSION` in [`document.py`](../../worker/mathimator_worker/document.py)
is part of every key. Bump it when the generated Python of an existing
document changes, or when the Manim pin changes (the spec treats every Manim
upgrade as a bump).
Opening a document written by an older generator then marks every beat dirty
and every export out of date, and the next save writes the current number. In
the same change, update the goldens in [`scenes`](../../scenes) and
`codegen.json`, and section 5 of the spec. A new beat kind, shape or easing
that leaves the code of existing documents unchanged needs no bump; the legacy
goldens check exactly that.
